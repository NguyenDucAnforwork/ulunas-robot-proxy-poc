# IOS_BUILD_AND_DEMO.md

**Written entirely in a Linux container with no macOS, no Xcode, and no physical iPhone 11.** Every step below that requires building, signing, running, or benchmarking is marked `BLOCKED_EXTERNAL` and must be performed by a person with that hardware. Nothing in this document was executed; it is a specification for that person to follow, with explicit template tables to fill in — never take numbers from this file as real results.

## 0. What exists right now

- `ios/UlunasDemo/` — a complete Xcode project (hand-written `project.pbxproj`, Swift sources, an Objective-C++ bridge) implementing the full audio pipeline described in the project brief: mic capture → resample to 16kHz → lock-free ring buffer → dedicated inference thread → `ulunas_process_hop()` → ring buffer → wired-headphone playback, plus a SwiftUI control/monitoring UI and WAV recording.
- `mobile/c_neon/include/ulunas_api.h` — the fixed C API contract (`ulunas_init`, `ulunas_process_hop`, `ulunas_reset`, `ulunas_destroy`) the Swift/ObjC++ bridge is written against.
- The runtime-free C **implementation** (the `.c` files satisfying that header) is being completed by a separate, concurrent workstream at `mobile/c_neon/` — check `MOBILE_BENCHMARK.md`'s "Runtime-free C" section for its exact status before starting step 2 below.

## 1. Prerequisites (for the person with the hardware)

- A Mac with Xcode 15+ installed.
- An iPhone 11 running a supported iOS version, connected via cable or on the same network (wireless debugging).
- An Apple ID (free tier is enough for a 7-day development signing; a paid developer account avoids the weekly re-sign).
- Wired (Lightning) headphones — **required** for live monitoring, since this project has no echo cancellation (see §5).

## 2. Opening and completing the project

1. `open ios/UlunasDemo/UlunasDemo.xcodeproj` (or double-click it in Finder).
2. Xcode may prompt to "resolve" the project the first time since it was hand-written outside Xcode, not generated by it — this is expected; let it index normally. If Xcode reports any file-reference issue, use File > Add Files to "UlunasDemo" to re-add the flagged file from its existing path rather than recreating it.
3. **Add the runtime-free C engine's source files** to the target: in the project navigator, right-click the "UlunasDemo" group > Add Files to "UlunasDemo", and select every `.c` file under `mobile/c_neon/` that implements `ulunas_api.h` (check `MOBILE_BENCHMARK.md` for the exact current file list — this project's pbxproj could not include them by path because the concurrent C-graph workstream's file list wasn't finalized at the time this iOS project was written). Also add `mobile/c_neon/generated/ulunas_weights.h` and `mobile/c_neon/src/kernels.h` to the header search path (already pre-added in the build settings: `HEADER_SEARCH_PATHS` includes `mobile/c_neon/include`; add `mobile/c_neon/src` and `mobile/c_neon/generated` alongside it if the implementation files live there).
4. Select the "UlunasDemo" project > Signing & Capabilities > set your Team (Apple ID) and a unique bundle identifier (the placeholder `com.example.UlunasDemo` will not be signable as-is).
5. Select your iPhone 11 as the run destination (not a simulator — a simulator run proves nothing about real hardware and must never be reported as a benchmark).
6. Build (Cmd+B). Fix any signing/provisioning prompts Xcode raises (all routine, Xcode-guided).

**Status: `BLOCKED_EXTERNAL`** — requires the Mac/Xcode/iPhone this environment doesn't have.

## 3. ONNX Runtime reference backend (optional, for the debug/comparison path)

The bridge (`UlunasBridge.mm`) gates ONNX Runtime behind `ULUNAS_ENABLE_ONNXRUNTIME_BACKEND`. To enable it:
1. Add `onnxruntime-objc` via Swift Package Manager (File > Add Package Dependencies, search `microsoft/onnxruntime-swift-package-manager`) or CocoaPods (`pod 'onnxruntime-objc'`).
2. Set the preprocessor macro `ULUNAS_ENABLE_ONNXRUNTIME_BACKEND=1` in Build Settings for the target.
3. Add the exported streaming ONNX model (`mobile/onnx_export/out/ulunas_finetuned_stream_simple.onnx`) as a bundled resource.
4. **Known gap, disclosed honestly**: `UlunasBridge.mm`'s ONNX code path currently only initializes the session; it does not yet port the host-side STFT/ISTFT framing and cache-packing logic (see the `NOTE` comment in that file) needed to actually drive the ONNX graph frame-by-frame. That porting work (straightforward — copy the logic already proven correct in `mobile/onnx_export/export_finetuned_stream.py` and `mobile/android_ref/src/main.cpp`) was not completed in this pass; it's a prerequisite before the ONNX backend can actually run, not just be initialized.

**Status: `NOT_RUN`** (partially implemented, not finished, not tested).

## 4. Live demo — 3 required noise scenarios

Per the project brief, demonstrate with wired headphones connected:
1. **Stationary fan noise** — play a steady fan/HVAC recording near the phone while speaking.
2. **Motor/UAV playback** — play a drone/UAV motor recording (e.g. from the robot-proxy dataset's public-source clips, see `ROBOT_PROXY_DATA.md`) near the phone while speaking.
3. **Changing-RPM/impulsive noise** — play a recording with RPM ramps or servo clicks (procedurally generated clips from `ROBOT_PROXY_DATA.md` work for this) while speaking.

For each: toggle Bypass on/off and confirm audibly through the headphones that Enhancement measurably reduces the background noise without destroying speech intelligibility. Record a short screen capture (Control Center > Screen Recording) showing the UI counters (RTF, inference time, underrun/overrun) live during each scenario.

**Status: `BLOCKED_EXTERNAL`** — no device to run this on.

## 5. Feedback-risk / no-AEC warning

This project deliberately has no acoustic echo cancellation. The app detects the current audio route (`AudioEngineManager.currentRoute`/`headphonesConnected`) and shows a prominent warning banner when no wired/Bluetooth output is detected, since playing enhanced audio through the built-in speaker while the mic stays open will feed back into the mic. **Always use wired Lightning headphones for the live-monitoring demo.** Bluetooth may be used for a casual demo only — never for latency/RTF measurements (Bluetooth adds its own, uncontrolled codec latency).
